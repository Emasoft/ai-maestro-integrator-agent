## Why the old pin had to go

[[TRDD-2581d9ca]] pinned every callsite to `@v2.136.1` because v2.137.0's
`[REPO LINT] (15 languages)` phase hung ~30 min on CI runners. That was correct at the
time. It stopped being correct on **2026-06-23**, when `claude-plugins-validation`
**#148** and **#149** were both closed and fixed in **v2.145.1** — released the same
hour. The pin then sat for six weeks defending a hazard that no longer existed, three
major versions behind (`v5.3.0` is latest).

**A stale pin is not a safe pin**, and this is the concrete demonstration: v2.136.1's
narrower ruleset was not protecting the tree from false positives, it was **hiding seven
real defects in our own code**. Bumping to v5.3.0 surfaced all of them at once.

## What the stale pin was hiding

| Sev | Rule | Site | Why it was a real defect |
|---|---|---|---|
| MAJOR | DTZ005 | `scripts/amia_pre_push_hook.py:105` | naive `datetime.now()` in a log line |
| MAJOR | DTZ005 | `scripts/amia_pre_issue_close_hook.py:94` | same |
| MAJOR | DTZ005 | `scripts/amia_stop_hook.py:212` | same |
| MAJOR | PLW1510 | `scripts/amia_stop_hook.py:242` | `subprocess.run` with an implicit `check` |
| MAJOR | UP045 | `scripts/amia_stop_hook.py:322` | `Optional[int]` on a ≥3.10 floor |
| MINOR | SC2221 | `.githooks/pre-push:34` | glob alternative that always overrides the next |
| MINOR | SC2222 | `.githooks/pre-push:34` | …and the next one, which could never match |

**The three DTZ005 are the ones that mattered.** A bare `%Y-%m-%d %H:%M:%S` is ambiguous
across machines and DST boundaries, so those log lines could not be correlated with
anything — and this project's own timestamp rule already forbids omitting the `%z`
offset. Fixed as `datetime.now(timezone.utc).astimezone().strftime("…%z")`: tz-aware
*and* offset-bearing.

`PLW1510` was resolved as an explicit **`check=False`**, not `check=True`. That helper's
contract is to RETURN the `CompletedProcess` so callers inspect `returncode` — its
timeout and missing-`gh` paths synthesize `returncode=1` for the same reason. `check=True`
would raise, and **a Stop hook that raises takes down the session it exists to report
on.** The fix makes a deliberate choice explicit rather than changing behaviour.

`SC2221`/`SC2222` looked alarming — a branch of the push gate that never executes — and
is **not** a functional hole. Verified empirically: `*python*scripts/publish.py*`
subsumes `*python*/scripts/publish.py*` (the leading `*python*` absorbs the `/`), and
both alternatives returned 0, so behaviour was always identical. Dead code, removed.

## Pin discipline retained

Re-baselining is **not** un-pinning. Still an immutable tag at every callsite:
`@main` 404s (CPV's default branch is `master`, #139), and bare `master` means a
CI-gating tool inherits upstream regressions silently — which is exactly how the
v2.137.0 hang reached CI in the first place. **A pin is a baseline to RE-MEASURE, not a
workaround to carry forward.**

## Two measurement traps hit while doing this — both nearly produced a false conclusion

1. **The stale uvx cache.** An earlier "latest CPV reports MAJOR=5" reading was taken
   against **v2.143.0** — older than the v2.145.1 fix — because `uvx` served a cached
   build. Always `--refresh` when measuring a *version* claim.
2. **The wrapper's exit code masked the tool's.** The run was wrapped as
   `{ …; echo "EXIT=$?"; } > file`, so the harness reported **exit 0** while CPV had
   actually exited **2**. The real code was only visible inside the captured file.
   **Read the verdict from the captured output, never from the exit status of a
   wrapper that ends in `echo`.**

A third, smaller one: a `grep --include=*.yml` sweep for remaining `v2.136.1` references
**silently returned nothing** while two workflows still carried the old pin. A per-file
direct check found them. A selector that drops inputs reports the same thing as a clean
tree.
